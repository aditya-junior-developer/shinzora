# UPI payments — the customer flow

The operator collects money into one UPI account. The customer pays by scanning the
operator's QR, then submits the transaction ID, and an administrator confirms it.
Nothing is ever marked paid by the interface.

## The flow, screen by screen

1. **Your UPI ID** — before any QR is shown, the customer types the VPA they will pay
   from (e.g. `name@okhdfc`). It is validated (`name@bank`), stored with the payment,
   and shown to the administrator, because that is the line that appears in the bank
   statement next to the credit.
2. **Amount + QR** — the amount to pay is the largest thing on the screen
   (`₹4,999`), with the payment reference underneath, and the operator's own QR image
   sits at the bottom of the panel. On a phone the QR is 240px wide and fully visible
   without scrolling sideways.
3. **"I have paid"** — asks for the UPI transaction ID (UTR) and submits.
4. **Confirmation** — "Payment submitted. You can close this page now. Your payment is
   confirmed within 24 hours and your plan becomes active the moment it is."

Closing the window, pressing Escape or reloading changes nothing on the server. There
is no code path in the browser that can mark a payment successful.

## Where the numbers come from

| Thing | Source |
| --- | --- |
| Amount | server-side catalogue in `payments/index.ts` — a client-sent amount is ignored |
| Payee VPA | secret `UPI_ID`, exposed publicly by `config` (it is printed on the QR anyway) |
| QR image | `public/assets/payments/upi-qr.png` — the operator's own poster |
| Reference | generated by the database (`SZ-XXXXXXXXXX`) |
| Status | `pending` → `awaiting_verification` → `verified` (admin or signed webhook only) |

If the QR image ever fails to load, the dialog falls back to a QR generated from the
`upi://` intent string, so a payment is still possible rather than showing a broken box.

## What the administrator sees

Admin → Payments → open a row:

* **Paid from (UPI ID)** — the payer's VPA, pulled out of the stored note
* **UTR** — the transaction ID the customer submitted
* **Customer note** — anything else the customer wrote
* Approve or reject; approving is the only way a plan/subscription changes

## Configuration

```bash
# Secrets for the payments function (on the hosted project)
supabase secrets set UPI_ID=manglampandey@fam UPI_PAYEE_NAME="Manglam Pandey"

# Local development (.env, not a secret — a UPI ID is public by design)
UPI_ID=manglampandey@fam
UPI_PAYEE_NAME=Manglam Pandey
PAYMENTS_MODE=manual_verification
```

The QR file is part of the deployable tree, so it ships with the site:
`public/assets/payments/upi-qr.png`. Replace that file to change the QR.

## Verified

* Live: `create` → `200`, ₹2,499 in paise, intent string carrying the VPA; `submit_proof`
  → `awaiting_verification`, note `Payer UPI: payer@okhdfc`; a malformed VPA → `400`.
* Local: same contract in the pre-launch sandbox, including the 24-hour confirmation copy.
* Browser: desktop 1440px and mobile 390px both render the amount and QR with no
  horizontal scroll, and no console errors.
