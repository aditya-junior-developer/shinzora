Documentation

Everything below describes what the platform actually does. Where a feature depends on an external provider — a registrar, a payment gateway, an AI key — the page says so instead of pretending.

Getting started

  1. Create an account at /auth/signup. Email confirmation is required before the dashboard opens.
  2. Answer the three onboarding questions: business name, what you are building, and how you sell.
  3. You land on the dashboard. The first useful step is usually Website Builder → New project.
No credit card to start. The free plan includes a working website project, the store, support and the assistant. Nothing is charged until you choose a paid plan or request a paid service.

Accounts and security

Signing in

Sign in at /auth/login with your email and password. Administrators use the same page — there is no separate admin login form, because a second login screen is a second thing to keep secure. The console lives at /admin and refuses non-administrators on the server.

Changing your password

Dashboard → Account settings → Security. The change is completed through the account provider, and the success message only appears after the provider confirms it.

Forgot your password

  1. Open /auth/forgot-password and enter your email.
  2. The reset email contains a single-use link that expires; the link returns you to the reset screen.
  3. Choose a new password. Used, expired or tampered links are refused rather than silently accepted.
Email delivery is part of the deployment. If reset mail does not arrive, the mail provider in the Supabase project is the thing to check — the platform will not claim a message was sent if the provider rejected it.

Website and app builders

A project has versions. Generating a site creates a new version with sections you can edit, reorder or delete. Publishing marks one version live and serves it at /site/?p=slug or on your own domain. Rolling back publishes an earlier version — nothing is destroyed.

Generation needs the ai function with a model key configured. Without it the builder returns a clear "AI is not configured" message and no half-generated content.

Online store

Add products with price, stock and description; orders arrive with the buyer's details and move through new → paid → shipped → delivered. Stock decrements when an order is recorded, and low stock is flagged on the overview.

Payments

UPI (the default)

  1. Choose a plan or a service. The amount comes from the server-side catalogue — a tampered browser cannot change it.
  2. Enter the UPI ID you will pay from. This is how the payment is matched in the bank statement.
  3. The amount and the Shinzora payment QR are shown. Pay the exact amount in any UPI app.
  4. Submit the UPI transaction ID. The record moves to awaiting verification and you may close the page.
Nothing is marked paid by the customer's browser. Only an administrator approving the payment — or a signature-verified gateway callback — can move a payment to verified, and that is the moment a plan or subscription changes.

Gateway (optional)

With Razorpay keys configured, orders are created server-side and confirmed by a signed webhook. Duplicate webhooks are ignored by reference, so a retried callback cannot double-credit an account.

Payment history

Your billing page lists your payments. Removing an entry from the customer's view hides it; the financial record itself stays in the database for accounting and audit, and remains visible to administrators.

Domains and subdomains

  • Free subdomain — every project can be published at your-slug.shinzora.in immediately.
  • Availability — checked against public registry data (RDAP), so "taken or free" is real and needs no account.
  • Price and registration — need a registrar connected to the deployment. Until then the row shows price on request and files a request rather than inventing a number.
  • Your own domain — add it here, create the DNS records shown, and the status stays pending until DNS actually resolves.

Service requests

Paid and managed services are requested from the dashboard and tracked with a status you can follow. Each request is linked to your account and, where relevant, to a business and a project.

Every request gets a reference such as SR-4F2A9C10 and moves through four stages: requested, approved, in progress and completed. A request can also end as rejected or cancelled, and the reason is shown on the card. You can follow all of this under Service requests in the dashboard, where each card shows its stage rail, the target date if one has been set, and any note Shinzora has written for you.

Shinzora contacts you about your request; you are never told to wait for a third-party call. Deadlines shown for a service are Shinzora's own targets, not a guarantee from any external provider.

Admin console

/admin is available to accounts with an administrator role, granted in the database — never from the browser. The console covers overview metrics, customers, payments (with approve and reject), service requests, subscriptions, projects, deployments, domains, orders, support, announcements, contact messages, activity and monitoring.

Payment approval is the only path that upgrades a plan. Every approval records who did it and when.

Monitoring

Incidents and events are recorded as they happen: sign-ins, server starts, browser errors, data changes, abandoned and failed payments, and admin actions. The monitoring view separates pre-launch test activity from customer activity so the two never mix. Logs never contain passwords, tokens or keys.

Pre-launch testing

The repository can run a local, self-contained environment with its own accounts and data so the product can be exercised without touching production records. It is a development surface: it is not deployed with the public site and it holds no customer data.

Deployment

The full walkthrough is in docs/DEPLOYMENT.md. In short:

# 1. database
supabase db push                      # migrations 0001–0005

# 2. edge functions (8 of them)
export SUPABASE_ACCESS_TOKEN=sbp_…
node scripts/deploy-functions.mjs
node scripts/smoke-functions.mjs --remote

# 3. secrets (server-side only)
supabase secrets set SHINZORA_AI_API_KEY=… SHINZORA_AI_MODEL=gemini-3.8-flash
supabase secrets set UPI_ID=… UPI_PAYEE_NAME="…"

The web app is a static build plus one serverless API entry point, so it deploys to any static host with function support. Configure the Supabase URL and publishable key in the environment; the service_role key is never part of the frontend.

Security model

  • Authentication is handled by the account provider; passwords never touch Shinzora's own storage.
  • Every server function verifies the caller's token before doing anything on their behalf.
  • Administrator rights are checked on the server for every admin action, not by hiding buttons.
  • Row-level security scopes reads and writes to the signed-in owner.
  • Secrets — AI keys, gateway secrets, service keys — live only in the server environment.
  • A payment is never inferred from interface state: closing a window, reloading or navigating changes nothing.

Questions

The assistant says AI is not configured

No model key is set for the deployment. Until one is, the assistant refuses rather than inventing an answer.

Domain search shows "price on request"

Availability is live from the public registry, but pricing needs a registrar account connected to the deployment.

I paid and nothing changed

Payments move to verified after review, normally within 24 hours. Check Billing for the status of the reference you submitted.
